사내 프로그램의 배포와 자동 업데이트를 맡는 file-server의 **서버 운영자용** 문서입니다.
각 프로그램을 빌드하고 올리는 방법은 해당 저장소 문서를 보세요.

## 1. 개요

```
 사내망 개발 PC                              file-server (사내, :9100)                     사용자 PC
 ──────────────                              ─────────────────────────                     ─────────
 빌드 (build.bat / Build.ps1)
   └─ Publish-FileServer.ps1 ─── HTTP ───▶  프로그램 자동 생성 (최초 1회)
        (토큰은 PC에 1회 저장)               새 버전 생성 → exe 업로드 → 배포
                                              └─ /<slug>/latest.json 갱신  ◀── 업데이트 확인 ── 프로그램
                                                 /<slug>/<exe>              ──▶ 다운로드 · SHA-256 검증 · 설치
 GitHub Actions: 빌드 · 테스트 검증만 (배포하지 않음)
```

- **GitHub 클라우드 러너는 사내 서버(211.231.121.41:9100)에 접속할 수 없습니다.** 그래서 배포는 사내망 PC에서 합니다.
- 클라이언트(One TaskBar, ICS-SCM)는 예전 IIS 방식과 같은 주소를 읽으므로 **프로그램 코드 수정이 필요 없습니다.**

| 클라이언트 요청 | 파일서버 응답 |
|---|---|
| `GET /<slug>/latest.json` | 배포중인 **stable** 버전 중 가장 높은 **숫자 버전**(`1.0.0.57`)의 `.exe` 정보 `{version,file,sha256,notes,mandatory,size,published_at}` |
| `GET /<slug>/<file>` | 해당 버전 exe (이어받기 지원). 업로드한 이름에 버전이 없으면 붙여서 제공: `OneTaskBar-Setup.exe` → `OneTaskBar-Setup-1.0.0.57.exe` |
| `GET /<slug>/defaults.json` 등 | 관리자 화면의 "고정 파일" |

**버전 규칙:** `X.Y.Z.<빌드 번호>` 숫자 4자리. 같은 버전은 다시 올릴 수 없고(파일이 다르면 거부),
서버의 최신 버전보다 낮은 버전도 기본으로 거부합니다.

## 2. 서버 설치 · 업데이트 · 전환

### 2-1. Docker 이미지를 PC에서 빌드해 서버로 옮기기 (권장)
서버에는 소스나 인터넷이 필요 없습니다. PC에는 Docker Desktop, Git, OpenSSH(`ssh`, `scp`)가 필요합니다.

**한 번에 (PowerShell, 저장소 루트에서)**
```powershell
git pull
.\tools\docker\Deploy-Image.ps1 -Server deploy@211.231.121.41
```
`Deploy-Image.ps1`은 이미지 빌드 → `file-server-image.tar` 저장 → 서버로 복사 → `docker load` →
`docker compose up -d --no-build` → healthy 확인까지 합니다. 이전 이미지는 `file-server:before-update`로 보관합니다.

- **처음 실행:** 서버에 `.env`가 없으면 `.env.example`로 만들고 멈춥니다. 서버에서 `.env`를 고친 뒤 다시 실행하세요.
  ```bash
  ssh deploy@211.231.121.41
  vi ~/file-server/.env      # FS_PORT=9100, FS_ADMIN_PASSWORD=..., FS_BASE_URL=http://211.231.121.41:9100
  ```
- 옵션: `-RemoteDir ~/file-server`(기본), `-Platform linux/amd64`(서버가 ARM이면 `linux/arm64`),
  `-SshOptions @('-i','C:\Users\me\.ssh\id_ed25519','-p','2222')`, `-SkipUpload`(이미지 파일만 만들기)

**수동으로 하려면**
```powershell
# 내 PC
$tag = Get-Date -Format yyyyMMdd-HHmm
docker build --platform linux/amd64 -t file-server:latest -t file-server:$tag .
docker save -o file-server-image.tar file-server:latest file-server:$tag   # 파이프(|, >) 금지: 파일이 깨짐
scp file-server-image.tar docker-compose.yml .env.example deploy@211.231.121.41:~/file-server/
```
```bash
# 서버
cd ~/file-server
[ -f .env ] || { cp .env.example .env; vi .env; }
docker image inspect file-server:latest >/dev/null 2>&1 && docker tag file-server:latest file-server:before-update
docker load -i file-server-image.tar
docker compose up -d --no-build        # --no-build: 서버에는 소스가 없음
docker compose ps                      # (healthy) 확인
```

| `.env` | 설명 |
|---|---|
| `FS_PORT` | 외부 포트. IIS를 대체하면 `9100` |
| `FS_ADMIN_USER` / `FS_ADMIN_PASSWORD` | 관리자 계정. **시작할 때마다** 이 값으로 맞춤 (최소 4자) |
| `FS_BASE_URL` | PC들이 접속하는 주소 `http://211.231.121.41:9100` |
| `FS_MAX_UPLOAD_MB` | 파일 1개 최대 크기 (기본 4096) |

### 2-2. Docker 없이 Windows 서비스로
```powershell
# PC에서 빌드 (make release 또는)
$env:CGO_ENABLED='0'; $env:GOOS='windows'; $env:GOARCH='amd64'; go build -o bin\ .\cmd\...
# 서버에서
$env:FS_ADMIN_PASSWORD='...'; .\server.exe -addr :9100 -data D:\services\file-server -base-url http://211.231.121.41:9100
```
상시 실행은 NSSM(`nssm install file-server C:\...\server.exe -addr :9100 -data D:\services\file-server`) 또는 작업 스케줄러(시스템 시작 시)로 등록합니다.

### 2-3. 기존 IIS "Auto Update Server"(9100) 대체
**A안 (권장): 같은 서버에서 교체 — 클라이언트 변경 없음**
1. 파일서버를 다른 포트(예: 8080)로 먼저 띄우고, 두 프로그램의 **현재 배포 버전을 같은 버전 번호로** 올립니다 (4절).
2. `http://<서버>:8080/onetaskbar/latest.json`이 IIS의 것과 같은 version/sha256인지 확인합니다.
3. IIS 사이트를 중지하고 `.env`의 `FS_PORT=9100`으로 바꾼 뒤 `docker compose up -d --no-build`.
4. 문제가 생기면 `docker compose stop` 후 IIS 사이트를 다시 시작하면 원상복구됩니다(IIS 폴더는 그대로 둠).

**B안: 다른 서버에서 운영** — IIS 9100 사이트를 URL Rewrite + ARR로 파일서버에 역방향 프록시하거나,
클라이언트의 업데이트 서버 주소를 바꾼 버전을 마지막으로 IIS에 배포합니다.

### 2-4. 운영 명령 (서버, `~/file-server`)
| 작업 | 명령 |
|---|---|
| 상태 / 로그 | `docker compose ps` / `docker compose logs -f --tail 100 file-server` |
| `.env` 반영 | `docker compose up -d --no-build` |
| 관리자 계정 적용 결과 | `docker compose logs file-server \| grep -i admin` |
| 롤백 | `docker tag file-server:before-update file-server:latest && docker compose up -d --no-build` |
| 오래된 이미지 정리 | `docker images file-server` → `docker rmi file-server:<태그>` |

**`docker compose down -v` 금지** — `-v`는 DB와 업로드 파일이 든 볼륨을 지웁니다.

### 2-5. 백업 / 복원
모든 데이터는 볼륨 `file-server_fs-data` 하나에 있습니다 (`alpine` 이미지 필요, 폐쇄망이면 `docker save alpine`으로 반입).
```bash
docker compose stop
docker run --rm -v file-server_fs-data:/data -v "$PWD":/backup alpine tar czf /backup/fs-backup-$(date +%Y%m%d).tgz -C /data .
docker compose start
# 복원
docker compose stop
docker run --rm -v file-server_fs-data:/data -v "$PWD":/backup alpine sh -c 'rm -rf /data/* && tar xzf /backup/fs-backup-YYYYMMDD.tgz -C /data'
docker compose start
```

## 3. 새 프로그램 추가

1. **slug 정하기:** 영문 소문자·숫자·`-` (예: `my-tool`). 업데이트 주소 `http://211.231.121.41:9100/<slug>/`가 되며 **바꿀 수 없습니다.**
2. **API 토큰:** 관리자 화면(`/#/admin`) → API 토큰 → 생성. 값은 한 번만 표시됩니다. 배포할 PC에서 처음 배포할 때 입력합니다.
3. **스크립트 복사:** 이 저장소의 `tools/Publish-FileServer.ps1`을 해당 저장소 `tools/`에 그대로 복사합니다 (UTF-8 BOM 유지).
4. **빌드 스크립트에 배포 단계 추가** (예):
   ```powershell
   & "$PSScriptRoot\Publish-FileServer.ps1" -Program my-tool -Name "My Tool" -File dist\my-tool.exe -NotesFile notes.md
   ```
5. **클라이언트:** 업데이트 주소 `<서버>/<slug>/latest.json`을 읽어 `version` 비교 → `file` 다운로드(같은 폴더 기준 상대 경로) →
   `sha256` 검증 → 교체. 기존 One TaskBar/ICS-SCM 코드와 같은 방식입니다. Go 프로그램은 `pkg/updater`를 쓸 수도 있습니다.

프로그램은 **첫 배포 때 자동으로 만들어지므로** 관리자 화면에서 미리 등록할 필요는 없습니다.

## 4. 프로그램 배포하기 (사내 PC)

보통은 각 저장소의 빌드 스크립트가 아래를 대신 실행합니다 (ics-scm: `build.bat publish`). 직접 실행하면:

```powershell
.\tools\Publish-FileServer.ps1 -Program ics-scm -Name "ICS-SCM" -File dist\ics-scm.exe -NotesFromGit v1.0.0
```

**처음 한 번:** 토큰을 물어봅니다. 서버에서 확인한 뒤 이 PC·이 Windows 사용자에게만 암호화해 저장하고(`%APPDATA%\FileServer\credentials.json`, DPAPI),
다음부터는 묻지 않습니다. 같은 PC의 다른 프로그램 배포도 이 토큰을 함께 씁니다.

**실행 화면 예**
```
Server: ics-scm stable 1.0.0.61
Local:  ics-scm.exe 1.0.0.62 (8.4 MB, sha256 3fa1c0d2e9b7)
Created version ics-scm 1.0.0.62
(업로드 진행률 표시)
Uploaded ics-scm.exe (windows-amd64) as ics-scm 1.0.0.62
Published ics-scm 1.0.0.62
latest.json: http://211.231.121.41:9100/ics-scm/latest.json
{"version":"1.0.0.62","file":"ics-scm-1.0.0.62.exe","sha256":"3fa1…","notes":"- …","mandatory":false,…}
```

**스크립트 없이 하려면 (웹 관리자 화면)**
`http://211.231.121.41:9100/#/admin` → 프로그램 → *새 버전 만들기*(버전·패치노트) → 초안에서 `windows-amd64` 선택 후 exe 업로드 → **배포**.
고정 파일(`defaults.json`, 설치 파일)은 프로그램 화면의 *고정 파일*에서 올립니다.

## 5. Publish-FileServer.ps1 / fsctl publish 레퍼런스

원본: 이 저장소 `tools/Publish-FileServer.ps1` (Windows PowerShell 5.1 · PowerShell 7, Windows/Linux).
`fsctl publish`(Go)는 같은 배포 규칙을 따릅니다 (토큰 저장 기능은 PowerShell 스크립트에만 있음).

| PowerShell | fsctl | 설명 |
|---|---|---|
| `-Server` | `-server` | 기본: `$env:FS_SERVER` → 이 PC에서 마지막으로 쓴 서버 → `http://211.231.121.41:9100` |
| `-Token` | `-token` | 기본: `$env:FS_TOKEN` → 저장된 토큰 → (대화형이면) 입력받아 저장 |
| `-Program` | `-program` | slug (필수) |
| `-Name` | `-name` | 최초 자동 생성 시 표시 이름 (기본: slug) |
| `-File`, `-Platform` (기본 `windows-amd64`) | `-file windows-amd64=경로` | 배포할 exe |
| `-Version` | `-version` | 기본: 파일 옆 `version.txt` → (Windows) exe 파일 버전 |
| `-Channel stable\|beta` | `-channel` | 기본 stable |
| `-Notes`, `-NotesFile` | `-notes`, `-notes-file` | 패치노트 (Markdown) |
| `-NotesFromGit <ref>` 또는 `<a>..<b>` | `-notes-from-git` | 커밋 제목으로 패치노트. `-Notes`/`-NotesFile`이 있으면 무시 |
| `-Mandatory` | `-mandatory` | 필수 업데이트 |
| `-Draft` | `-draft` | 업로드만 (배포는 관리자 화면에서) |
| `-FixedFile <경로[]>` | `-fixed` | 버전과 무관한 고정 파일 (같은 이름은 교체) |
| `-AllowOlder` | `-allow-older` | 서버 최신보다 낮은 버전 허용 (유지보수 빌드) |
| `-SaveToken` | – | 토큰을 확인 후 저장 (`-File` 없으면 저장만) |
| `-ForgetToken` | – | 이 서버용 저장 토큰 삭제 후 종료 |
| `-SkipIfUnconfigured` | `-skip-if-unconfigured` | 토큰이 없으면 아무것도 안 하고 exit 0 |

**동작 순서 (여러 번 실행해도 안전)**
1. 토큰 확인 (`/api/v1/auth/me`) — 거부되면 401 오류. 저장된 토큰이 거부되면 `-ForgetToken` 후 다시 입력.
2. 서버의 현재 버전 표시. 로컬 버전이 더 낮으면 중단 (`-AllowOlder`로 허용).
3. 프로그램이 없으면 생성.
4. 버전 없음 → 생성 → 업로드(진행률) → 배포.
   초안 → 이어서 진행 (같은 플랫폼의 다른 파일은 교체, 저장된 패치노트 유지).
   배포됨 + 같은 SHA-256 → "already published", **exit 0**. 배포됨 + 다른 SHA-256 → **exit 1**. 회수됨 → **exit 1**.
5. 고정 파일 업로드, 마지막에 서버의 `latest.json` 출력.

**종료 코드:** 0 = 배포됨 / 이미 배포됨 / 초안으로 남김 / 건너뜀, 1 = 그 밖의 모든 오류.
**`$GITHUB_OUTPUT`이 있으면:** `version`, `status`(`published`/`already-published`/`draft`), `latest_json`을 기록합니다.

**토큰 저장소**
| OS | 위치 | 보호 |
|---|---|---|
| Windows | `%APPDATA%\FileServer\credentials.json` | DPAPI (현재 Windows 사용자만 복호화 가능) |
| Linux/macOS | `~/.config/fileserver/credentials.json` | 파일 권한 600 |

## 6. 릴리스 관리

| 상태 | 공개 페이지 | `latest.json` | 파일 변경 | 가능한 작업 |
|---|---|---|---|---|
| 초안 | 숨김 | 제외 | 가능 | 배포, 삭제 |
| 배포중 | 표시 | 대상 | 불가 | 패치노트 수정, 회수, 초안으로 |
| 회수됨 | 숨김 | 제외 | 불가 | 복원 |

- **회수(yank):** 문제 버전을 내리면 `latest.json`이 이전 버전으로 돌아갑니다. 단 클라이언트는 "더 높은 버전"만 설치하므로
  이미 설치한 PC는 내려가지 않습니다 → 번호를 올린 수정 버전을 배포하세요.
- **베타 채널:** `-Channel beta`로 올리면 일반 `latest.json`에는 나오지 않습니다. 시험 PC의 업데이트 주소를
  `…/<slug>/latest.json?channel=beta`로 지정하세요. `-beta.1` 같은 문자 버전은 .NET이 읽지 못하므로 숫자 버전을 쓰세요.
- **필수 업데이트:** `-Mandatory` 또는 관리자 화면 체크. `latest.json`의 `mandatory`, `/api/v1/update`의 `mandatory`로 전달됩니다.
- **고정 파일:** `defaults.json`(One TaskBar 회사 기본 설정), `ICS-SCM-Setup.exe`(항상 최신 설치 파일)처럼
  버전과 무관한 파일. `-FixedFile` 또는 관리자 화면에서 교체합니다. `latest.json`이라는 이름은 쓸 수 없습니다.

## 7. (선택 · 향후) CI 자동 배포와 self-hosted runner

현재는 쓰지 않습니다. 사내망에 상시 켜진 Windows PC가 생기면 그 PC를 GitHub Actions self-hosted runner로 등록해
main 병합 시 자동 배포할 수 있습니다 (러너 PC는 GitHub로 나가는 443만 필요, 외부 → 사내 포트 개방 불필요).

1. 저장소 → Settings → Actions → Runners → New self-hosted runner → Windows, 안내 명령을 그 PC에서 실행 (서비스로 설치).
2. 저장소 시크릿 `FS_SERVER`, `FS_TOKEN` 등록.
3. 배포 job만 사내 러너에서 실행:
   ```yaml
     publish:
       needs: build
       runs-on: [self-hosted, windows]
       if: github.ref == 'refs/heads/main'
       steps:
         - uses: actions/checkout@v5
           with: { fetch-depth: 0 }
         - uses: actions/download-artifact@v4
           with: { name: <빌드 artifact>, path: dist }
         - shell: pwsh
           env: { FS_SERVER: "${{ secrets.FS_SERVER }}", FS_TOKEN: "${{ secrets.FS_TOKEN }}" }
           run: ./tools/Publish-FileServer.ps1 -Program <slug> -File dist/<exe> -SkipIfUnconfigured
   ```
러너는 해당 저장소에만 등록하고, 공개 저장소에는 쓰지 마세요 (외부 PR 코드가 사내 PC에서 실행될 수 있음).

## 8. 보안 · 문제 해결

**보안**
- 업로드·수정은 관리자 로그인(세션 쿠키) 또는 API 토큰만 가능. 다운로드와 `latest.json`은 누구나.
- API 토큰은 서버에 해시로만 저장되고 생성 때 한 번만 보입니다. PC를 바꾸거나 사람이 바뀌면 관리자 화면에서 **폐기 후 재발급**하세요.
- 배포 PC의 토큰은 DPAPI로 그 Windows 사용자만 읽을 수 있습니다. 공용 계정에 저장하지 마세요.
- 모든 파일은 SHA-256으로 검증되고, 배포된 버전의 파일은 바꿀 수 없습니다.

**문제 해결**
| 증상 | 원인 · 조치 |
|---|---|
| `Cannot reach the file server ... (211.231.121.41:9100)` / 시간 초과 | 사내망 밖이거나 서버가 꺼짐. 사내 PC에서 `http://211.231.121.41:9100/healthz` 확인. GitHub 클라우드 러너에서는 원래 접속 불가 (7절) |
| `401` / `token ... was rejected` | 토큰 폐기·오타. `-ForgetToken` 후 다시 실행해 새 토큰 입력 |
| `older than ... already published` | 로컬 빌드 번호가 서버보다 낮음 (오래된 체크아웃?). `git pull` 후 재빌드, 의도한 경우 `-AllowOlder` |
| `already published with a different file` | 같은 버전으로 다른 빌드. 커밋을 하나 더 쌓아 버전을 올려 재빌드 |
| `latest.json` 404 | 배포중인 stable 숫자 버전에 `.exe`가 없음 (초안이거나 beta) |
| 로그인 안 됨 | `docker compose logs file-server \| grep -i admin`. 5회 실패 시 잠시 차단 |
| `Deploy-Image.ps1` 실패 | `ssh deploy@서버` 접속 확인, 서버의 `docker compose logs --tail 50`, 롤백은 2-4절 |
